# Dashboard implementation rules

These rules apply to `apps/dashboard`. The project-specific [ADS catalog](../../docs/design/ATLASSIAN-CATALOG.md) and [implementation guide](../../docs/design/IMPLEMENTATION.md) explain component selection. Official references are linked there; project rules are not quotations from Atlassian.

- The user authorizes shadcn/ui alongside Atlaskit. Use shared controls in src/components/controls for buttons, inputs, textareas, menus, tabs and status badges; use the shared shadcn Table wrapper. Retain Atlaskit form validation, select, checkbox, feedback and modal primitives where they preserve verified behavior. Do not add competing controls per page. See docs/design/SHADCN.md.
- The user now requires the Frappe CRM design system. Use Lucide through `src/components/icons`, the pinned Frappe UI tokens under `src/design/frappe`, and `frappe-system.css` component recipes. Keep the Frappe-supplied Inter font and accessible icon wrappers. See docs/design/FRAPPE-UI-REVIEW.md. Retain existing form, permission and focus behavior.
- Verify the real installed examples at `/design-system` in development before changing component presentation. Preserve the Compiled styling integration. Use the self-hosted Inter font mapping in typography.css; the user explicitly requires Inter for all app typography, including code. Keep custom CSS on wrappers; do not override Atlaskit table cells, heading typography or control internals. Compare development and production rendering after bundler/style changes.
- Use the shared `Page`, `Table`, dialog and feedback components. Extend the shared primitive when the same behavior is needed on several pages.
- Use semantic product colors in ui.css, mapped to retained ADS surfaces and text. Use ADS spacing tokens in wrapper CSS and Tailwind utilities in owned shadcn primitives. Keep palette values centralized, support dark and increased contrast, and preserve Inter. Geometric layout sizes and breakpoints may be explicit.
- Use Heading for section structure, Text for prose, MetricText for metrics. Keep one h1 per page and ordered heading levels. Use Title Case for documentation headings, navigation and menu labels; keep descriptions in sentence case, acronyms intact, and code/API identifiers unchanged.
- Choose components for actual tasks. Inventory coverage does not authorize adding unsupported product features, fake counts, non-working tabs or every catalog dependency.
- Avoid new deprecated or caution-marked APIs when there is a supported alternative. Existing pinned APIs can remain until their replacement is verified; do not make unrelated dependency upgrades.
- Internal links use React Router. Actions use buttons. Current breadcrumbs are text. Every icon-only action needs an accessible name.
- Preserve loading, first-use empty, filtered-empty, permission-denied and error states. Important errors remain in the affected view; success flags confirm completed writes. Loading is announced politely.
- Every form has associated labels, inline validation, submission state and recovery without discarding entered data. Prevent duplicate writes. Destructive confirmations start on Cancel and disable repeated confirmation while pending.
- Overlay focus is contained and restored on close. Mobile navigation makes the background inert, closes on Escape and navigation, and supports keyboard use. Menus and modal portals must remain usable.
- Test narrow screens, long content, keyboard navigation, zoom/reflow, light, dark and increased contrast. Scroll wide tables inside their container, never the whole page.
- Report remote SMTP acceptance truthfully; never label it inbox delivery. Preserve role/permission checks and backend authorization.
- Run `pnpm --filter @mp/dashboard typecheck`, `pnpm --filter @mp/dashboard test`, `pnpm --filter @mp/dashboard build` and `pnpm audit:design` for relevant UI work. Use isolated fixtures for browser checks and clearly distinguish them from live-backend validation.

- Keep task pages free of automatically injected Guide buttons. Documentation is opened through Help or universal search, without a Documentation link in the main workspace sidebar. Its dedicated view shows one searchable article-navigation rail with expandable section links and a wide reader, following the supplied GreenPellets product-datasheets reference. Keep the global header and a Back to Workspace action. Omit Version/API version blocks and a duplicate right-hand contents rail. On mobile, article navigation expands above the reader.
- Product help includes only published help and developer guides. Keep its navigation, labels and quota instructions synchronized with real routes and capabilities; exclude internal architecture and design-audit documents.

- Match Frappe CRM surfaces: main canvas uses `--surface-base`, sidebar uses `--surface-gray-1`, menus/dialogs use Frappe elevation tokens. This supersedes the former same-surface rule by the user's explicit request for the exact Frappe design system.

- Main workspace navigation is one continuous list, without group-collapse state. Documentation has a dedicated article tree with expandable section links and a fixed heading/title search. Use consistent 14px interface labels and Lucide icons. Desktop app navigation collapse remains available outside documentation.

- The user removed breadcrumbs and requested a flatter layout. Keep page headings and dedicated editor titles, without breadcrumb trails. The shell fills the viewport; main content and sidebar navigation scroll independently, and the account stays at the bottom. Product corners are 4px on controls/panels and 8px on dialogs; keep upstream palette tokens unchanged.

- Standard pages use a 64px top header with brand on the left and a single avatar account menu on the right, centered universal search with a distinct background, and Help/notifications on the right. The sidebar begins below the header and contains navigation. Universal search opens a permission-aware dialog for pages, guides and supported records, including from Ctrl/Cmd+K; never route it directly to email filters. Mobile keeps the same actions in a compact header, and the automation canvas retains its editor toolbar.
- Resource table rows stay 40px high. Keep cells on one line, truncate long values with ellipsis and expose full values on hover. Wide tables scroll horizontally inside their region without widening the page.

- Use one avatar menu at the right of the header, after Notifications, Help and Settings icons. It includes profile identity, Profile, Personal Settings, a nested Theme menu, the current Workspace submenu and Log Out. The left header displays only the brand; workspace identity is inside the avatar menu. Workspace create/switch actions require real backend support; do not add fake options or unread counts. Do not add a second account dropdown. Documentation's article sidebar has a visible Documentation heading above its search. Settings is a modal with a 224px section sidebar and independently scrolling content; preserve the background route and filters.
- The workspace name dropdown has no favicon beside its label; branding appears once in the header. Notifications open a top-right floating modal above the current page, with Escape/outside-click dismissal, contained scrolling and focus restoration. Use 14px controls/navigation, 12px metadata and consistent 20px page titles; reading prose can retain its larger reading scale.
