# Automations implementation

Added 26 October 2026. Source: `packages/core/src/automations.ts`, `apps/api/src/routes/automations.ts`, database migration `0010_aspiring_iceman.sql`, dashboard `Automations.tsx`, and Morphmailer SDK.

## Execution and lifecycle

- Projects own workflows, immutable published versions, event receipts, runs and step journals. All five new tables enforce tenant RLS; routes also scope project IDs. Owners/admins/developers and full-access keys receive explicit automation permissions; read-only roles get read permission.
- Draft updates use optimistic revisions. Publishing validates reachable acyclic graphs with at most 50 nodes, unique step IDs, verified sender domains and valid recipient-facing unsubscribe URLs. Existing runs remain pinned to their published graph and publishing identity.
- Custom events carry a project-scoped idempotency key, existing contact ID and scalar properties. Concurrent identical requests return one receipt and the same runs. Conflicting reuse returns 409. Optional workflow schemas validate required property names and primitive types atomically before any enrollment.
- Email, delay, wait-for-event and condition steps are durable. Conditions use typed equals/not-equals/exists/contains/greater-than/less-than with AND/OR groups. Contact fields and event fields are available; HTML substitution escapes user values. Published template content can be copied into a step as an immutable snapshot from the editor.
- Each worker tick locks one due run. The step journal and email admission commit together, so crashes and concurrent workers do not requeue an admitted email. Delay timestamps survive restart; wait steps poll matching future contact events every five seconds until timeout, with separate event and timeout branches. Paused waiters retain receipts for later evaluation.
- Pausing prevents new enrollment and new steps and holds queued automation mail. Resume releases those holds. A late pause observed immediately before transport submission restores the recipient for a later attempt. As with cancellation, already-started SMTP handoffs cannot be recalled.
- Run cancellation prevents pending steps and suppresses queued mail before handoff. Failed-step retry retains successful step journals. Quota/rate-limit failures back off for 60 seconds automatically. Other admission failures remain visible for manual retry.
- Current contact subscription/archive/address, suppression and sender eligibility are checked before admission; the dispatcher checks consent and run cancellation again before SMTP. Publishing API-key revocation/expiry is rechecked at handoff. Restricted-domain keys cannot submit broad events, resume, retry or republish existing workflows; initial publish checks every sender domain.
- Dry-run testing traverses saved drafts without creating mail. It previews delays and branches and stops at wait-for-event. A completed run means orchestration completed, not inbox delivery. Inspect linked email delivery state separately.

## Metrics endpoint

`GET /v1/automations/:id/metrics?days=14` requires `automations:read`. The range accepts 1–90 UTC calendar days, including today through the request timestamp; the response supplies exact `from` and `to` bounds. Every aggregate is restricted to the caller's organization/project, the automation and its latest published version. The response includes that immutable version's definition so a graph cannot accidentally display mutable draft nodes with published statistics. Unpublished drafts return `version:null`, `workflow:null` and zero-filled day buckets.

Metrics describe a cohort of runs **created in the selected window**, using their current status at query time. Daily run totals group by run creation date; these are not historical completion-event dates. Email activity groups by email admission date for emails linked to steps in the same cohort. Emails and steps also have their own window bounds. Separate run/step/email aggregates in one SQL snapshot prevent join multiplication and do not depend on paginated run lists.

Email counts are distinct messages, not recipients. A message counts as `server_accepted` when at least one recipient is currently `REMOTE_ACCEPTED`; `MTA_ACCEPTED` stays `pending`. This records receiving-server acceptance, never inbox placement, opens or clicks. `queued` includes QUEUED/SCHEDULED; `pending` covers admission/dispatch/retry/deferral/uncertain transport states; failed includes FAILED/REJECTED. Bounced, suppressed and cancelled are separate outcomes. The workflow normally creates one recipient per email; if a message has multiple recipients, it can appear in more than one outcome category, while `total` still counts that message once.

Node `executions` count persisted `(run_id,node_id)` step journals whose start time is in the cohort window. Retrying a failed step updates its existing journal and does not count as an additional execution. Untouched published nodes have zero-filled counts. The trigger's enrollment count is `runs.total`. Skipped contacts may enroll without executing any node; completed orchestration is not equivalent to delivery.

Metrics verification adds isolated PostgreSQL scenarios for unpublished states and permission boundaries, UTC midnight bounds under a non-UTC database timezone, immutable published-version graphs, cohorts larger than a page, and distinct-email aggregation despite duplicate step/recipient references.

## Scope and limits

Initial implementation verification: 9 isolated PostgreSQL automation scenarios and 6 existing Broadcasts regression scenarios passed, along with 32 core unit tests, 9 SDK tests and 3 API tests. Typechecks and builds passed. Migration0010 was applied to the local database. Production dashboard fixture checks passed at desktop/mobile light and desktop dark widths. The test transport records messages locally; external inbox delivery was not exercised.

The editor displays an automatically arranged connected workflow canvas. Select a node to edit its settings, add a step at a terminal branch, and use local scrolling, zoom or Fit width to navigate. Connections are set explicitly in the inspector; dragging nodes or drawing edges is not implemented. Test workflow and publishing settings open in side sheets. Event schemas are attached to workflows, not a separate versioned organization-wide event catalog. Wait predicates match event name and contact; branches can then inspect properties. There is no arbitrary JavaScript, webhooks as workflow actions, automatic contact lifecycle trigger generation, cron trigger, or external CRM connector. Applications explicitly post custom events. Event receipts and history currently have no retention purge; operators must size storage accordingly. No external mail was sent during verification.
