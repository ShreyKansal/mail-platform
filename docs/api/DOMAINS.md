# Domains

You can only send from domains you have proved you control. Adding a domain generates the DNS records to publish. Once the required records are found in DNS, sending is enabled.

| Method | Path | Permission |
| --- | --- | --- |
| `POST` | `/v1/domains` | `domains:manage` |
| `GET` | `/v1/domains` | `domains:read` |
| `GET` | `/v1/domains/{id}` | `domains:read` |
| `POST` | `/v1/domains/{id}/verify` | `domains:manage` |
| `DELETE` | `/v1/domains/{id}` | `domains:manage` |

## Add a domain

```bash
curl -X POST http://localhost:3000/v1/domains \
  -H "Authorization: Bearer $MP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"notify.example.com","return_path_label":"bounce"}'
```

| Field | Rules |
| --- | --- |
| `name` | The domain or subdomain you will send from. It is normalized to lowercase ASCII (internationalized names become A-labels). It must have at least two labels and a valid top-level domain. Platform-owned domains are refused. |
| `return_path_label` | Optional, default `bounce`. One lowercase DNS label; your custom Return-Path becomes `<label>.<name>`. |

**Response `201`**: a domain object (see below) in status `pending`, with `sending_enabled: false`. Adding the same name twice in one organization returns `409 conflict`.

Tip: send from a subdomain such as `notify.example.com` to keep transactional reputation separate from your main domain. A verified domain also authorizes `From` addresses on its subdomains, which are signed with the parent domain's DKIM key and so still align under relaxed DMARC.

## Generated records

For a domain `D` with return-path label `L`:

| `purpose` | Type | Host | Value | Required |
| --- | --- | --- | --- | --- |
| `ownership` | TXT | `_mp-challenge.D` | `mp-verification=<token>` | **yes** |
| `dkim` | TXT | `<selector>._domainkey.D` | `v=DKIM1; k=rsa; p=<2048-bit public key>` | **yes** |
| `return_path_mx` | MX (priority 10) | `L.D` | The platform bounce host | no |
| `return_path_spf` | TXT | `L.D` | `v=spf1 include:<platform SPF include> -all` | no |
| `dmarc` | TXT | `_dmarc.<organizational domain of D>` | `v=DMARC1; p=none;` (suggested starting point) | no (recommended) |

- The ownership token is random and unique to this domain record in your organization. Another account's token can never verify your domain, and yours can't verify theirs.
- The DKIM private key is generated by the platform, stored encrypted, and never returned by the API.
- **Return-Path**: until both `return_path_mx` and `return_path_spf` are valid, mail uses the platform's shared bounce domain. DMARC still passes through DKIM alignment. Once both are valid (`custom_return_path_active: true`), bounces return to `L.D` and SPF aligns too.
- **DMARC** is checked at the organizational domain (e.g. `_dmarc.example.com` for `notify.example.com`). `p=none` is reported as `partial` (monitoring only). Enforcement (`quarantine` or `reject` at `pct=100`) is reported as `valid`.

## Verification

`POST /v1/domains/{id}/verify` checks every record immediately and returns the updated domain. It may be called once per domain every 10 seconds (`429 rate_limited` otherwise). The platform also re-checks automatically: every 2 minutes during the first hour, every 15 minutes while pending after that, and every 6 hours once verified.

### Record statuses

| `status` | Meaning |
| --- | --- |
| `valid` | Found and correct. |
| `pending` | Your authoritative nameservers already serve the correct value, but cached answers elsewhere have not expired yet (propagation). |
| `missing` | No matching record found. |
| `invalid` | A record exists but is wrong (a different token, a mismatched or truncated key, an SPF record lacking the include, an MX pointing elsewhere, bad syntax). `detail` explains. |
| `partial` | DMARC exists but is monitoring-only (`p=none`) or `pct` < 100. |
| `conflict` | Several competing records: two SPF records, two DKIM records for the selector, two DMARC records, or extra MX hosts on the Return-Path. |
| `temp_error` | DNS timed out or failed temporarily. Retry later. |
| `resolution_failed` | DNS returned an unexpected error. |

`observed` lists what was actually found in DNS, which helps with debugging.

### Domain statuses

| `status` | Meaning |
| --- | --- |
| `pending` | Waiting for the required records. |
| `verified` | Ownership and DKIM are valid; `sending_enabled` is true. |
| `failed` | Required records were not found within 72 hours of creation, **or** a verified domain later lost its ownership or DKIM record (DNS drift). Sending is disabled until the records are restored and checked again. |
| `disabled` | Removed by you (see below). It can no longer be verified or used. |

Temporary DNS errors never downgrade a verified domain. Only a definite `missing`, `invalid` or `conflict` result for the ownership or DKIM record does. Changes to and from `verified` emit the `domain.verified` and `domain.verification_lost` [webhook events](WEBHOOKS.md#events).

### Domains claimed by another account

Only one organization may hold verified ownership of a given domain name at a time. If another account has already verified it, verification returns `409 conflict`. Contact support if you control the domain.

## Remove a domain

`DELETE /v1/domains/{id}` stops sending from the domain immediately.

```json
{ "id": "0d0e…", "result": "disabled" }
```

- `deleted`: the domain had never sent mail, so it and its keys were removed.
- `disabled`: the domain has email history, so it is kept for audit with `status: disabled`. Its DKIM key is retired and the ownership claim released. To use the name again, add it as a new domain.
